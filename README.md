# Monster Order Desk

Рабочее место кладовщика для выдачи заказов со склада. Приложение получает заказ и остатки из 1С:Управление торговлей через OData, позволяет проверить данные получателя, создать непроведённый документ реализации в 1С и просмотреть, сохранить или напечатать PDF-документ выдачи.

Приложение рассчитано на работу в доверенном внутреннем контуре. Пользовательская аутентификация и хранение истории получателей в текущей версии не реализованы.

## Возможности

- поиск заказа по номеру документа или `Ref_Key` (GUID);
- загрузка состава заказа, склада, единиц измерения и ставок НДС;
- получение доступного остатка по номенклатуре, складу и характеристике;
- отдельные статусы по каждой строке: «В наличии», «Недостаточно», «Остаток не получен»;
- расчёт суммы строки, НДС и суммы с НДС с поддержкой обычных и расчётных ставок;
- адаптивный интерфейс для desktop и mobile;
- форма получателя: фамилия, имя, отчество, телефон и email;
- клиентская и серверная валидация обязательных данных;
- определение пола и склонение ФИО в дательный падеж для текста «Выдать кому?»;
- экран подтверждения с реквизитами заказа, получателем, итогами и предупреждениями по остаткам;
- создание непроведённого документа `Document_РеализацияТоваровУслуг` в 1С;
- защита от повторной записи: перед POST выполняется поиск реализации по исходному заказу;
- проверка созданного документа повторным GET-запросом;
- формирование PDF с кириллицей, таблицей товаров, итогами и местами для подписей;
- просмотр PDF прямо в приложении с перелистыванием страниц и изменением масштаба;
- печать PDF: через системный диалог Electron с выбором принтера или через браузерную печать;
- сохранение PDF через системный диалог Electron либо обычное скачивание в браузере;
- индикатор доступности сервиса и данных 1С, обновляемый каждые 30 секунд;
- поиск номенклатуры по EAN-13 через форму и показ остатка отдельно по каждому складу.

## Пользовательский сценарий

### Выдача заказа

1. Ввести номер заказа или его `Ref_Key` и нажать «Найти».
2. Проверить реквизиты заказа, состав, цены, НДС и статусы остатков.
3. Заполнить данные получателя.
4. Перейти на экран подтверждения и проверить итоговые данные.
5. Подтвердить выдачу.
6. Приложение повторно получает заказ, находит или создаёт реализацию в 1С, проверяет результат и формирует PDF.
7. На экране успеха можно открыть просмотр накладной, выбрать принтер и напечатать документ или сохранить его повторно.

На всех этапах отображается компактный индикатор прогресса. Во время запросов к 1С кнопка начала нового
заказа временно скрыта, чтобы случайным нажатием не прервать текущую операцию.

Недостаточный или неизвестный остаток отображается как предупреждение, но автоматически не блокирует выдачу: окончательное решение принимает кладовщик.

### Проверка остатка по штрихкоду

1. В едином поле поиска отсканировать EAN-13, ввести его вручную или выбрать сохранённый
   штрихкод демо-базы.
2. Убедиться, что форма распознала EAN-13 и кнопка изменилась на «Проверить остаток».
3. Нажать «Проверить остаток».
4. Сверить карточку номенклатуры, общий остаток и значения по каждому складу.

Единое поле различает GUID заказа, номер заказа и EAN-13 по формату. Последовательность из 13 цифр
с неверной контрольной цифрой не отправляется ни в поиск заказа, ни в поиск товара. Поиск остатка
только читает данные 1С и не создаёт документы.

Тестовые штрихкоды хранятся в `src/shared/demoBarcodes.ts` и показываются в интерфейсе:

| EAN-13          | Ожидаемая номенклатура        |
| :-------------- | :---------------------------- |
| `4600100000014` | Бумага офисная А4, 500 листов |
| `4600100000021` | Ручка шариковая синяя         |
| `4600100000038` | Папка-регистратор 75 мм       |

Это данные внешней демо-базы 1С: названия и остатки могут измениться.

## Подключение к 1С

Приложение использует опубликованный OData endpoint 1С:Управление торговлей 11.5.

- **Base URL по умолчанию для демо-стенда:** `https://goshift.ru/demo_ut/odata/standard.odata`
- **Аутентификация:** Basic Auth
- **Конфигурация:** переменные окружения (см. таблицу ниже)

### Переменные окружения

**Обязательные:**

- `ODATA_BASE_URL` — URL OData endpoint 1С
- `ODATA_USERNAME` — имя пользователя для Basic Auth
- `ODATA_PASSWORD` — пароль для Basic Auth

**Опциональные (с дефолтными значениями):**

- `ODATA_TIMEOUT` — таймаут запросов к 1С в мс (по умолчанию `15000`)
- `ODATA_CONNECTION_CHECK_TIMEOUT` — таймаут проверки соединения в мс (по умолчанию `5000`)
- `ODATA_RETRY_DELAY` — задержка между повторами запроса в мс (по умолчанию `1000`)
- `PORT` — порт сервера (по умолчанию `3000`)
- `NODE_ENV` — режим сервера; для `npm start` используется `production`
- `CORS_ORIGINS` — разрешённые внешние источники через запятую; пустое значение в текущем сервере
  разрешает любой origin, поэтому для web-развёртывания задавайте явный список
- `VITE_CONNECTION_CHECK_INTERVAL` — интервал проверки соединения на клиенте в мс (по умолчанию `30000`)
- `VITE_TOAST_TIMEOUT` — время показа уведомлений в мс (по умолчанию `5000`)

Секреты не должны попадать в исходный код, README, snapshots или логи. Подробная локальная конфигурация находится в `.env.example`, если файл присутствует в рабочем окружении.

### Конфигурация Windows-приложения

В установленной и portable-версиях параметры OData задаются через кнопку «Настройки» в шапке приложения. При первом запуске окно настроек открывается автоматически. Перед сохранением приложение проверяет доступность сервиса и корректность авторизации.

Настройки сохраняются в файле `config.json` в каталоге профиля Electron (`app.getPath('userData')`, обычно `%APPDATA%\Monster Order Desk`). Пароль не хранится в исходниках или рядом с exe-файлом. После изменения параметров требуется перезапустить приложение, чтобы встроенный сервер применил новую конфигурацию. В desktop-режиме сервер слушает только `127.0.0.1` на динамическом порту и недоступен из внешней сети.

В текущей версии `config.json` хранится без шифрования средствами приложения: защита файла
опирается на права доступа профиля Windows. Не копируйте этот файл в тикеты, архивы и каталоги
общего доступа. При смене пользователя компьютера удалите его после закрытия приложения.

## Быстрый старт

Требования: Node.js 20 и npm.

```bash
npm install
npm run dev
```

В режиме разработки запускаются два процесса:

- backend: `http://localhost:3000`;
- frontend: `http://localhost:5173`.

Перед запуском необходимо задать OData-переменные окружения. Для production-сборки:

```bash
npm run build
npm start
```

Скрипт `build` собирает клиент и сервер и копирует серверные assets, включая шрифты PDF.

Для настольной сборки под Electron:

```bash
npm run build:electron
```

Команда `build:electron` выполняет сборку клиента, сервера и компилирует точки входа Electron (`dist-electron/main.js` и `dist-electron/preload.js`). Для упаковки дистрибутивов Windows (NSIS-инсталлятор и Portable .exe) используется:

```bash
npm run package:win
```

NSIS-инсталлятор создаётся на русском языке, позволяет выбрать папку установки и добавляет ярлыки
в меню «Пуск» и на рабочий стол. Portable-версию можно запускать без установки.

### Просмотр и печать PDF

После формирования документа кнопка «Просмотр накладной» открывает встроенный просмотрщик. В нём доступны:

- переход между страницами клавишами `←`/`→` и кнопками панели;
- изменение масштаба от 60% до 250% (нажатие на процент возвращает 100%);
- сохранение PDF через системный диалог или скачивание в браузере;
- печать на выбранный принтер в Electron. Если список принтеров недоступен, используется системный диалог;
- закрытие окна клавишей `Esc` или кнопкой «Закрыть».

В обычном браузере печать открывает стандартный диалог печати браузера. PDF-данные передаются в просмотрщик
в памяти текущего сценария и не отправляются в отдельный внешний сервис.

## Windows-дистрибутив

Команда `npm run package:win` создаёт два x64-файла в `dist-electron-build/`:

- `Monster-Order-Desk-<version>-x64-setup.exe` — NSIS-инсталлятор;
- `Monster-Order-Desk-<version>-x64-portable.exe` — portable-версия без установки.

В состав обоих вариантов входит текстовая инструкция `resources/README.txt`. Для работы приложения нужны Windows 10 или новее, 64-разрядная система и сетевой доступ к опубликованному OData endpoint 1С. Node.js и npm конечному пользователю не нужны: они требуются только для разработки и сборки.

Приложение не включает 1С, базу данных, учётные записи или сетевой VPN. Их предоставляет организация. Для выдачи заказа пользователь должен иметь права чтения заказов, номенклатуры, складских остатков и чтения/создания непроведённых реализаций в опубликованном OData-сервисе.

## Актуальная схема Electron и разработки

Desktop-версия состоит из трёх частей:

- главный процесс Electron запускает Express на `127.0.0.1` и выбирает свободный порт;
- preload публикует в renderer только типизированный `desktopBridge` с методами настроек,
  сохранения PDF, печати и получения принтеров;
- React-клиент обращается к встроенному API по относительным `/api`-маршрутам и не подключается
  к 1С напрямую.

В development `npm run dev:electron` запускает Express на порту `3000`, Vite на `5173`, а Electron
загружает Vite через `VITE_DEV_SERVER_URL`. В production-потоке `npm run build:electron` собирает
клиент в `dist/client`, сервер в `dist/server` и точки входа Electron в `dist-electron`; `npm run
package:win` упаковывает эти артефакты в x64 NSIS и Portable-дистрибутивы.

Текущие важные ограничения desktop-режима:

- `config.json` содержит credentials в открытом виде внутри профиля пользователя;
- renderer изолирован (`contextIsolation: true`, `nodeIntegration: false`), но Chromium sandbox
  отключён (`sandbox: false`);
- CSP добавляется главным процессом только вне development;
- Express по умолчанию разрешает любой CORS-origin, поэтому loopback-привязка не заменяет
  полноценную аутентификацию локального API;
- отдельной аутентификации операторов и разграничения ролей нет.

Приоритеты дальнейшей разработки: хранение секрета через `safeStorage` или другой защищённый
механизм Windows, runtime-валидация IPC-входов, строгая политика CORS для desktop API, проверка
возможности включения Chromium sandbox и автоматизация сборки/подписывания релизов.

## API приложения

Все маршруты доступны с префиксом `/api/documents`.

### `GET /api/documents/status`

Проверяет доступность OData-сервиса и чтение данных. Возможные статусы:

```json
{ "status": "connected" }
```

Также возвращаются `disconnected` или `degraded`; для них может быть поле `detail`.

### `POST /api/documents/orders/search`

Ищет заказ по номеру или `Ref_Key`. Для номера поддерживается вариант без префикса `00`, если в 1С хранится полный номер.

```json
{ "orderRef": "00000123" }
```

Ответ содержит `order`, `lines` и `totals`. Каждая строка включает артикул, наименование, единицу измерения, количество, цену, ставку НДС, рассчитанные суммы, остаток и `stockStatus`.

### `POST /api/documents/preview`

Возвращает расчёт и нормализованные данные получателя без записи в 1С и без формирования PDF. В этом маршруте `orderRef` должен быть именно GUID заказа.

```json
{
  "orderRef": "2da145f0-d5fc-11f1-a0b3-48df371887e9",
  "customer": {
    "lastName": "Воронцов",
    "firstName": "Пётр",
    "middleName": "Аркадьевич",
    "phone": "8 (999) 123-45-67",
    "email": "p.vorontsov@example.com"
  }
}
```

В ответе возвращаются `fullNameGenitive`, `fullNameDative`, телефон в формате `+7...`, email, реквизиты заказа, строки и итоги.

### `POST /api/documents/generate`

Повторно получает заказ, находит существующую реализацию или создаёт новую, проверяет её через 1С и возвращает PDF-файл:

- `Content-Type: application/pdf`;
- `Content-Disposition: attachment`;
- `X-Document-Number` с номером реализации в Base64.

Создаваемый документ имеет `Posted: false`, `ХозяйственнаяОперация: "РеализацияКлиенту"` и ссылку на исходный заказ. Данные получателя используются для PDF и не записываются в документ 1С.

### `POST /api/documents/check`

Проверяет данные получателя и наличие реализации по заказу перед выдачей. Если реализации ещё нет, маршрут создаёт её, проверяет чтение созданного документа и возвращает номер. При найденной реализации возвращается `alreadyExists: true`; после этого интерфейс предлагает скачать PDF без повторной записи.

### `GET /api/documents/products/barcode/:barcode`

Проверяет формат и контрольную цифру EAN-13, находит товар в
`InformationRegister_ШтрихкодыНоменклатуры`, получает карточку номенклатуры и возвращает
остатки из `AccumulationRegister_ТоварыНаСкладах/Balance`, сгруппированные по складам.
Ответ содержит `barcode`, `article`, `name`, `unit`, массив `balances` и `totalBalance`.
Если регистр не вернул строк, `balances` остаётся пустым, а `totalBalance` равен `null`.

## Расчёты и данные

Источник каждого поля разделён по ответственности:

- данные заказа, товара, склада и остатков приходят из 1С OData;
- данные получателя вводятся пользователем и живут только в текущем сценарии;
- суммы, статусы остатков, нормализация телефона и склонение ФИО рассчитываются приложением.

Денежные вычисления находятся в `src/server/services/calculations.ts` и выполняются в целых копейках:

- сумма строки: количество умножить на цену с округлением до копейки;
- НДС считается от округлённой суммы строки;
- округление выполняется по правилу half-up (`1.265` превращается в `1.27`);
- итоги складывают уже округлённые значения строк;
- при цене с НДС сумма без НДС рассчитывается выделением налога из валовой суммы;
- поддерживаются ставки `22%`, `20%`, `13%`, `10%`, `0%`, `Без НДС`, расчётные формы
  `22/122`, `20/120`, `10/110` и другие корректные числовые ставки в форматах `N%` и `N/M`.

Во внешнем API суммы передаются в рублях, а внутреннее округление выполняется в копейках.

Остаток берётся из виртуальной таблицы `AccumulationRegister_ТоварыНаСкладах/Balance` по номенклатуре, складу и характеристике. Все строки ответа регистра суммируются по прочим измерениям. Используется `ВНаличииBalance`; `КОтгрузкеBalance` отдельно не вычитается.

## Обработка ошибок и повторные запросы

Для безопасных GET-запросов OData предусмотрены до трёх попыток с задержкой 1 секунда при сетевых ошибках, `408`, `429` и ответах `5xx`. POST создания документа намеренно не ретраится, чтобы не создать дубликат. Перед записью дополнительно выполняется поиск реализации по `ЗаказКлиента_Key`.

Ошибки API содержат машинный `code`, сообщение и признак `retryable`, когда он предусмотрен маршрутом. Пустой или невалидный заказ и обязательные поля получателя считаются неповторяемыми ошибками; временная недоступность 1С может быть повторена после проверки состояния сервиса.

Комплексный UI E2E-тест (`e2e/user-scenarios-pdf.spec.ts`) последовательно проверяет эталонные

`output-artifacts/web/screenshots/`), скачивает сгенерированный PDF-документ выдачи (сохраняет в
`output-artifacts/web/pdf/`) и останавливается при первом успешно созданном новом документе реализации
в 1С. Задача интегрирована в VS Code (`Tasks: Run Task` → `Test: User Scenarios with Screenshots and PDF`).

Десктопный UI E2E-тест Electron (`e2e/electron-scenarios.spec.ts`) запускает реальное приложение в среде Electron,
проверяет доступность системного моста `desktopBridge`, проходит сценарий выдачи и изолированно сохраняет
скриншоты и PDF-файлы накладных в выделенную директорию `output-artifacts/electron/`:

- `output-artifacts/electron/screenshots/` — пошаговые скриншоты окон Electron;
- `output-artifacts/electron/pdf/` — сохранённые через IPC накладные в формате PDF.
  Задача доступна в VS Code (`Tasks: Run Task` → `Test: Electron Scenarios with Screenshots and PDF`) или через `npm run test:e2e:electron`.

## Ограничения текущей версии

- остатки предупреждают о проблеме, но не блокируют создание реализации;
- создаётся непроведённый документ, автоматическое проведение в 1С не выполняется;
- отдельной аутентификации и разграничения прав пользователей нет;
- данные получателя не сохраняются в приложении и не записываются в документ 1С;
- форма принимает ввод или сканирование одного EAN-13 за один поиск;
- OData-пагинация по `@odata.nextLink` поддержана для табличной части заказа и справочника единиц измерения;
- склонение редких, иностранных и неоднозначных имён может потребовать ручной проверки;
- PDF использует встроенный DejaVu Sans с поддержкой кириллицы;

## Как развивается проект

Используется простой цикл для внутреннего приложения без отдельного бюджета на инфраструктуру:

1. фиксируем основной поток и источники данных;
2. небольшими итерациями реализуем поиск, остатки, форму, расчёты, запись и PDF;
3. после каждой части запускаем узкие проверки, перед выпуском — тесты, typecheck, lint, форматирование и сборку;
4. выпускаем обычную сборку клиента и сервера, а ошибки выдачи и расчётов ставим выше косметических улучшений.

На текущем этапе не нужны отдельная база данных, микросервисы, Kubernetes, платный CI/CD и SLA. Масштабирование инфраструктуры рассматривается только при подтверждённом росте нагрузки.

- кеширование справочных данных выполняется только в памяти процесса и сбрасывается после перезапуска.
