# Инструкции для агентов

## Контекст проекта

Monster Order Desk — внутреннее веб-приложение для выдачи заказов со склада через 1С OData. Сервер на Express и клиент на React/TypeScript собираются отдельно. Подробные требования и описание потоков находятся в `README.md` и `ARCHITECTURE.md`; команды сверяйте с `package.json`.

Эти правила относятся ко всему репозиторию. Если указание пользователя противоречит этому файлу, действует указание пользователя. Для вложенных каталогов новых файлов инструкций не создавать без отдельного запроса.

## Главные принципы

- Сначала корректность данных, расчётов и записи в 1С, затем интерфейс и оптимизация.
- Не подменять отсутствующие или ошибочные данные нулями, пустыми заглушками или вымышленными значениями.
- Для каждого отображаемого поля сохранять источник: 1С OData, ввод пользователя или расчёт по требованиям.
- Делать небольшие изменения в пределах задачи и не переписывать несвязанные пользовательские изменения.
- Не добавлять базу данных, очередь, микросервис, авторизацию или новую зависимость без явной необходимости и объяснения.

## Границы кода

- Все HTTP-вызовы 1С размещать в `src/server/services/odataClient.ts`.
- Денежные расчёты размещать в `src/server/services/calculations.ts`; внутри использовать целые копейки.
- Нормализацию телефона, определение пола и склонение ФИО размещать в `src/server/services/nameUtils.ts` или общем модуле, если это уже предусмотрено контрактом.
- Общие типы запросов и ответов размещать в `src/shared/types.ts`.
- Маршруты Express должны проверять входные данные, вызывать сервисы и формировать HTTP-ответ; бизнес-правила в маршрутах не дублировать.
- Клиентская часть (`src/client`) обращается только к API приложения, а не к 1С напрямую.

## Типы, стиль и данные

- Сохранять строгий TypeScript: не ослаблять `strict`, `noUnusedLocals`, `noUnusedParameters` и связанные проверки без обоснования.
- Не использовать `any`; для неизвестных данных применять `unknown` и явно проверять его форму. Ответы внешнего API проверять во время выполнения (в проекте используется Zod).
- Соблюдать настройки `.eslintrc.json` и `.prettierrc`: 2 пробела, одинарные кавычки, точка с запятой, ширина строки 100.
- Не менять публичные поля API без обновления общего типа, серверного маршрута, клиента и проверок.
- Для OData учитывать GUID, пагинацию и реальные названия полей 1С. Перед изменением запросов или преобразований сверяться с локальным контрактом `metadata.xml`; не угадывать имена сущностей, реквизитов и типов. Ошибки и отсутствие остатков должны оставаться различимыми.
- Для НДС отдельно проверять обычные ставки и расчётные ставки (`N/М`), цены с НДС и без НДС, дробное количество и округление.

## Безопасность и внешние данные

- Секреты (в том числе `.env`, Basic Auth, токены и пароли) читать только из окружения. Не открывать их без необходимости, не печатать в терминал, логи, тесты, снимки или ответы.
- Не добавлять реальные секреты в документацию и примеры; использовать `.env.example` с фиктивными значениями.
- GET к 1С можно повторять только по существующей политике клиента. POST создания документа не повторять автоматически: сначала проверить идемпотентность и поиск уже созданной реализации.
- Запись, удаление, проведение документов, изменение общей демо-базы и другие внешние изменения выполнять только по явному запросу пользователя. Для проверки использовать чтение или изолированные тестовые данные.
- Не редактировать `node_modules`, `dist`, `playwright-report` и `test-results` вручную; это создаваемые артефакты.

## Рабочий порядок

1. Определить затронутый поток и прочитать владеющий модуль, контракт и ближайшие тесты.
2. Сформулировать проверяемую причину проблемы и внести минимальное изменение.
3. Сразу выполнить узкую проверку, относящуюся к изменению.
4. Проверить изменённые файлы и статус рабочей папки; не включать посторонние изменения.
5. Перед завершением сообщить команды, которые действительно запускались, их результат и оставшиеся ограничения.

## Журнал изменений

- Технические изменения вести в `Changelog.md`; это единый журнал проекта, новые записи добавлять сверху, не переписывая историю.
- Добавлять запись только при заметном изменении поведения или устройства системы: исправление ошибки, новый или изменённый API-контракт, расчёты и НДС, OData-запросы и идемпотентность, безопасность, PDF, пользовательский сценарий, конфигурация сборки или существенные тесты.
- Не добавлять отдельные пункты для перестановки строк, исправления опечаток, форматирования, временных файлов, сгенерированных артефактов и каждого изменённого файла.
- Одна запись должна кратко отвечать на три вопроса: что изменилось, зачем это сделано и как проверено. Указывать дату, затронутую область и фактически запущенные команды; непройденные проверки помечать как ограничения.
- Если изменение влияет на API, схему данных, переменные окружения или совместимость, явно описать это и указать требуемое действие при обновлении.
- Не записывать в журнал пароли, токены, Basic Auth, персональные данные и содержимое `.env`; использовать только безопасные идентификаторы и обобщённые описания.
- Документационные изменения отражать в журнале только если они меняют рабочие правила, контракт или процесс разработки; обычное редактирование текста в журнал не добавлять.

## Команды проверки

- Типы клиента и сервера: `npm run typecheck`.
- Модульные тесты серверных сервисов и маршрутов: `npm test`.
- Проверка E2E (Playwright, Chromium и Mobile Chrome): `npm run test:e2e`. Она запускает собранный сервер и требует настроенного окружения 1С, если тест не перехватывает запросы.
- Линтер: `npm run lint`; автоисправление применять только к изменённым файлам и после просмотра diff.
- Форматирование: `npm run format:check`; исправление — `npm run format` только по согласованному набору файлов.
- Сборка: `npm run build`; после неё не редактировать созданные файлы вручную.
- Для UI запускать `npm run dev` и проверять основной сценарий на desktop и mobile, если изменение затрагивает интерфейс.

Не заявлять, что проверка пройдена, если команда не запускалась, завершилась ошибкой или проверяла не тот уровень. При сбое отделять ошибку кода от отсутствующих внешних условий (например, недоступной 1С).

## Риск и проверка изменений

- Критический риск: неверные суммы/НДС, утечка персональных данных, неправильная запись документа в 1С.
- Высокий риск: неверный остаток, повторная запись при повторе запроса, отсутствие проверки входа, повреждённый PDF, скрытая ошибка OData.
- Для изменений расчётов добавлять граничные тесты; для API проверять успешный ответ и ошибочные входные данные; для записи проверять повторный вызов и подтверждение созданного документа; для UI проверять состояния загрузки, ошибки, пустое состояние и успешный сценарий.
- В замечании или отчёте указывать файл, способ воспроизведения, ожидаемое и фактическое поведение.

## Запрещённые действия без запроса

- `git commit`, `git push`, публикация релиза и изменение истории Git.
- Сброс или массовое изменение общей базы 1С.
- Удаление файлов и каталогов, кроме явно названных пользователем.
- Установка production-зависимостей без проверки совместимости с Node.js 20 и React 18.
