# Архитектура Monster Order Desk

Monster Order Desk — рабочее место кладовщика для выдачи заказов со склада через 1С OData.

## Назначение

Приложение получает заказ и остатки из 1С OData, формирует JSON preview, записывает черновик реализации в 1С и создаёт PDF с таблицей товаров и итогами. Кладовщик может просмотреть, сохранить и напечатать сформированный документ.

## Текущий статус реализации

### ✅ Реализовано (Этапы 1–3)

- **Настольная архитектура Electron (Embedded Express Desktop)**
- Управляемый запуск Express внутри Electron с динамическим портом loopback `127.0.0.1`
- Single-instance lock и корректная остановка сервера при завершении приложения
- Изолированный рендерер (`contextIsolation: true`, `nodeIntegration: false`)
- Renderer не получает доступ к Node.js и Electron напрямую: разрешённые операции проходят через
  типизированный `desktopBridge` из preload
- Конфигурация OData через IPC и файл профиля пользователя `app.getPath('userData')/config.json`; перед сохранением настроек выполняется проверка подключения к 1С
- Desktop-мост (`desktopBridge`) для нативного сохранения PDF-накладной через системный проводник
- Сборка бандла `dist-electron` (`npm run build:electron`) и упаковка под Windows через electron-builder

- **PDF и печать**
  - Сервер формирует PDF через PDFKit и возвращает его как `application/pdf`.
  - Клиент сохраняет документ в памяти текущего сценария и открывает `PDFViewer` на базе `react-pdf`/`pdfjs-dist`.
  - В Electron печать и список принтеров проходят через типизированный `desktopBridge`; в браузере используется стандартный диалог печати.

- **Дизайн-система Monster Ads**
  - CSS-переменные с брендовым синим акцентом (`--color-brand-primary`) и семантическими цветами состояний
  - Светлая и тёмная деловые темы с переключением в шапке и сохранением выбора в `localStorage`
- Базовые UI-компоненты: Button, Input, Card, Badge, Alert

- **Компоненты UI**
  - `BrandHeader` — шапка с логотипом, индикатором статуса 1С OData, кнопкой настроек (в desktop-режиме) и переключателем темы
  - `OrderSearch` — поиск заказа по номеру, Ref_Key или EAN-13 штрихкода
  - `OrderSummary` — реквизиты заказа (номер, дата, склад)
  - `OrderLinesTable` — адаптивная таблица товаров с трансформацией в карточки на mobile/ТСД
  - `StockStatusBadge` — семантические бейджи остатков (В наличии / Недостаточно / Остаток не получен)
  - `CustomerForm` — форма данных получателя с валидацией email и телефона
  - `IssueSummary` — панель итогов с расчётом НДС и предупреждениями по остаткам
  - `ConfirmationStep` — экран проверки перед записью в 1С с предупреждениями и реквизитами
  - `SuccessState` — экран успешной выдачи с номером созданного документа реализации
  - `ToastContainer` — всплывающие уведомления

- **Backend API и OData интеграция**
  - Express сервер с маршрутами `/api/documents/status`, `/api/documents/orders/search`, `/api/documents/preview`, `/api/documents/check`, `/api/documents/generate`, `/api/documents/test-connection` и `/api/documents/products/barcode/:barcode`; маршрут штрихкода проверяет EAN-13 и возвращает номенклатуру с остатками, сгруппированными по складам
  - Полноценная интеграция с 1С OData через `ODataClient`:
    - Корректная схема `Document_ЗаказКлиента` с `ЦенаВключаетНДС` и реквизитами
    - Точный endpoint остатков: `/AccumulationRegister_ТоварыНаСкладах/Balance` с
      `ВНаличииBalance`
    - Создание документа выдачи `Document_РеализацияТоваровУслуг` со ссылкой `ЗаказКлиента_Key` и `ХозяйственнаяОперация: 'РеализацияКлиенту'`
    - Защита от повторной записи (идемпотентность: поиск уже созданного документа перед записью)
    - Retry logic для сетевых ошибок, 408, 429 и 5xx на безопасных GET-запросах
    - Проверка существования созданного документа реализации (`verifySalesDocument`)

- **Бизнес-логика**
  - Расчёт сумм и НДС в целых копейках (`calculations.ts`)
  - Поддержка обычных и расчётных ставок НДС
  - Склонение ФИО получателя в дательный падеж («Выдать кому?») по правилам русской морфологии через библиотеку Petrovich (`nameUtils.ts`, `nameDeclension.ts`)
  - Генерация PDF-документа выдачи товара (PDFKit)

## Анализ desktop-режима и текущие технические риски

### Жизненный цикл

Главный процесс получает single-instance lock, загружает `config.json`, переносит параметры OData
в окружение встроенного Express и запускает сервер на loopback. После определения фактического
порта создаётся `BrowserWindow`: в development он открывает `VITE_DEV_SERVER_URL`, в упакованной
версии — локальный Express. При завершении приложения обработчик `before-quit` сначала закрывает
HTTP-сервер и только затем завершает процесс. Повторный запуск не создаёт второе окно, а переводит
уже открытое окно на передний план.

### Граница renderer/main

Preload предоставляет только следующие IPC-операции: чтение и запись конфигурации, получение
адреса API, сохранение PDF, печать PDF и получение принтеров. Произвольный `ipcRenderer` в React
не доступен. Данные, передаваемые через bridge, сейчас описаны TypeScript-интерфейсами, но не
проверяются runtime-схемой; при расширении IPC-контракта нужна валидация формы и размера входа.

### Безопасность

- Express слушает только `127.0.0.1`, но глобальная CORS-политика по умолчанию допускает любой
  origin; для web-режима `CORS_ORIGINS` должен быть явным.
- `contextIsolation` и `nodeIntegration: false` уменьшают поверхность renderer, однако
  `sandbox: false` остаётся текущим компромиссом совместимости и требует отдельной проверки перед
  включением sandbox.
- CSP задаётся главным процессом только в production. В development политика намеренно остаётся
  менее строгой для Vite HMR.
- credentials сохраняются в `userData/config.json` без шифрования приложением. Текущая защита —
  ACL профиля Windows; следующий шаг — `safeStorage` и минимизация времени жизни пароля в памяти.
- Пользовательская аутентификация отсутствует, поэтому desktop-приложение рассчитано на доверенный
  компьютер и контролируемую сеть 1С.

### Разработка и релиз

Основной feedback loop: узкий unit/route-тест → `typecheck` → lint/format → сборка нужного слоя.
Для Electron добавляется `build:electron`, затем реальный E2E через Playwright Electron API.
Финальная Windows-проверка выполняется `package:win`; результатом являются x64 NSIS и Portable.
Сборка не подписывает код автоматически, поэтому перед распространением нужно добавить code signing,
проверку версии и публикацию checksum/релизных заметок.

### Приоритетный технический backlog

1. Шифровать пароль через `safeStorage` и не хранить его в обычном JSON.
2. Ввести Zod-схемы для IPC payloads и ограничить длину base64 PDF до ожидаемого размера.
3. Разделить CORS-политику для desktop и web и добавить защиту локального API от вызовов чужих
   страниц.
4. Проверить включение `sandbox: true` и оставить `sandbox: false` только при подтверждённой
   несовместимости.
5. Добавить CI для typecheck, unit/E2E без записи в общую 1С и повторяемой Windows-сборки.

### 🔄 Запланировано (развитие)

- Генерация PDF с QR-кодом для складского учёта

### Упрощённый цикл развития

Проект развивается короткими итерациями вокруг одного рабочего сценария: найти заказ, проверить остатки, заполнить получателя, создать черновик реализации и скачать PDF. Сначала уточняются требования и контракты 1С, затем небольшими частями меняются сервер, интерфейс и проверки. После каждого изменения запускается узкая проверка, а перед выпуском — общие тесты, проверка типов, линтер, форматирование и сборка.

Для текущего внутреннего масштаба достаточно одного сервера и переменных окружения. Отдельная база данных, микросервисы, очередь, контейнерная оркестрация, платный CI/CD и сложный мониторинг в архитектуру не входят. К масштабированию возвращаемся только при подтверждённой нагрузке.

- `src/server/services/odataClient.ts` — единственная граница HTTP-вызовов к 1С.

- `src/server/routes/documents.ts` — валидация запроса, координация сервисов и HTTP-ответы; бизнес-правила сюда не добавлять.
- `src/shared/types.ts` — публичный контракт между клиентом и сервером.
- `src/client/` не обращается к 1С напрямую; только к API приложения.

## Потоки данных

### 1. Поиск и загрузка заказа

```
Клиент (idle)
  → вводит Ref_Key заказа
  → POST /api/documents/orders/search

Сервер:
  → получает заказ из 1С: Document_ЗаказКлиента(Ref_Key)
  → для каждой строки получает остаток: AccumulationRegister_ТоварыНаСкладах_Balance
  → рассчитывает суммы с учётом НДС
  → возвращает OrderSearchResponse с расчётами и остатками

Клиент (order-loaded)
  → отображает OrderSummary + OrderLinesTable + CustomerForm
```

### 2. Проверка остатка по штрихкоду

```
Клиент (idle)
  → вводит значение в единое поле поиска или выбирает пример из demoBarcodes.ts
  → распознаёт GUID заказа, номер заказа либо EAN-13
  → для 13 цифр проверяет контрольную цифру и не отправляет неверный EAN-13
  → GET /api/documents/products/barcode/:barcode

Сервер:
  → повторно проверяет EAN-13
  → находит ссылки номенклатуры и характеристики в регистре штрихкодов
  → получает карточку номенклатуры и строки регистра остатков
  → группирует строки по складам, не подменяя отсутствие данных нулём
  → возвращает ProductStockSearchResponse

Клиент (idle)
  → показывает товар, общий остаток и остатки по складам
```

Этот поток выполняет только GET-запросы и не изменяет данные 1С. Тестовые штрихкоды демо-базы
хранятся в общем модуле `src/shared/demoBarcodes.ts`, который используют интерфейс и E2E-сценарий.

### 3. Формирование документа выдачи

```
Клиент (order-loaded)
  → заполняет данные получателя (CustomerForm)
  → переходит к подтверждению
  → POST /api/documents/check

Сервер:
  → повторно получает актуальные данные заказа
  → ищет существующую реализацию по ЗаказКлиента_Key
  → при отсутствии создаёт черновик Document_РеализацияТоваровУслуг (Posted=false)
  → проверяет чтение реализации из 1С

Клиент:
  → для новой реализации сразу вызывает POST /api/documents/generate
  → для существующей реализации запрашивает подтверждение скачивания

Сервер:
  → повторно получает актуальные данные заказа
  → повторно использует найденную реализацию, не создавая дубликат
  → генерирует PDF с данными получателя
  → возвращает PDF-файл

  Клиент (success)
    → сохраняет PDF в памяти текущего сценария
    → показывает SuccessState с номером документа
    → по запросу открывает PDFViewer, сохраняет или печатает PDF
```

### 4. Состояния сценария (WorkflowState)

Фактический поток перед генерацией включает промежуточную проверку `/api/documents/check`: сервер повторно проверяет заказ и получателя, ищет реализацию по `ЗаказКлиента_Key`, создаёт её только при отсутствии и подтверждает чтение документа через 1С. Поэтому повторное нажатие не должно приводить к повторной записи. После этого `/api/documents/generate` повторно получает актуальные строки, формирует PDF и передаёт номер документа в заголовке `X-Document-Number`.

```typescript
type WorkflowState =
  | 'idle' // Начальное состояние, форма поиска
  | 'loading-order' // Загрузка заказа из 1С
  | 'order-loaded' // Заказ загружен, показана таблица и форма
  | 'editing-recipient' // Зарезервированное состояние редактирования получателя
  | 'ready-to-generate' // Данные получателя готовы к подтверждению
  | 'checking' // Проверка реализации перед записью
  | 'confirm-existing' // Реализация уже найдена
  | 'generating' // Формирование документа
  | 'success' // Документ успешно создан
  | 'error'; // Ошибка на любом этапе
```

## Интеграция с 1С OData API

### Базовый URL и аутентификация

```
Демо URL: https://goshift.ru/demo_ut/odata/standard.odata
Учётные данные задаются только через переменные окружения.
Auth: Basic Authentication
```

В установленной Windows-версии URL, логин и пароль вводятся через окно настроек и сохраняются в профиле пользователя Electron. При запуске они загружаются главным процессом в переменные окружения встроенного Express-сервера. Исходный код, пакет приложения и README не содержат реальные credentials.

### Доступные сущности

#### Справочники (Catalogs)

- `Catalog_Номенклатура` — товары и услуги
  - Ref_Key (Guid), Code, Description, Артикул, ВидНоменклатуры_Key, ЕдиницаИзмерения_Key
- `Catalog_Склады` — склады
  - Ref_Key, Code, Description, ТипСклада
- `Catalog_Партнеры` — партнёры (контрагенты)
- `Catalog_Контрагенты` — юридические лица
- `Catalog_СтавкиНДС` — ставки НДС
- `Catalog_Валюты` — валюты
- `Catalog_Организации` — организации
- `Catalog_Пользователи` — пользователи системы

#### Документы (Documents)

- `Document_ЗаказКлиента` — заказ клиента
  - **Шапка:** Ref_Key, Number, Date, Posted, Партнер_Key, Контрагент_Key, Организация_Key, Валюта_Key, Склад_Key, Менеджер_Key, Статус, СуммаДокумента, ЦенаВключаетНДС, НалогообложениеНДС, Комментарий
  - **Navigation:** Товары (табличная часть)

- `Document_ЗаказКлиента_Товары` — строки заказа
  - Ref_Key, LineNumber, КодСтроки, Номенклатура_Key, Характеристика_Key, Количество, Цена, Сумма, СтавкаНДС_Key, СуммаНДС, СуммаСНДС, Склад_Key, ЗаказКлиента_Key

- `Document_РеализацияТоваровУслуг` — реализация товаров/услуг (документ выдачи)
  - **Шапка:** Ref_Key, Number, Date, Posted, ЗаказКлиента_Key, Партнер_Key, Контрагент_Key, Организация_Key, Валюта_Key, Склад_Key, Менеджер_Key, Ответственный_Key, ЦенаВключаетНДС, НалогообложениеНДС, ХозяйственнаяОперация, Согласован, Комментарий
  - **Navigation:** Товары (табличная часть)

#### Регистры накопления (Accumulation Registers)

- `AccumulationRegister_ТоварыНаСкладах/Balance` — виртуальная таблица остатков товаров на складах
  - **Измерения:** Номенклатура_Key, Характеристика_Key, Назначение_Key, Склад_Key, Помещение_Key, Серия_Key
  - **Ресурсы:** ВНаличииBalance (свободный остаток), КОтгрузкеBalance

#### Регистры сведений (Information Registers)

- `InformationRegister_ШтрихкодыНоменклатуры` — штрихкоды номенклатуры
  - **Ключ:** Штрихкод (String)
  - **Поля:** Номенклатура_Key, Характеристика_Key, Упаковка_Key

### Обработка ошибок OData API

#### Стандартный формат ошибки OData

```json
{
  "odata.error": {
    "code": "BadRequest",
    "message": {
      "lang": "ru",
      "value": "Ошибка при обработке запроса"
    },
    "innererror": {
      "message": "Детальное описание ошибки",
      "type": "System.Exception"
    }
  }
}
```

#### HTTP коды и стратегии обработки

| Код | Описание                 | Стратегия                                   | Повтор  |
| --- | ------------------------ | ------------------------------------------- | ------- |
| 200 | Успешный запрос          | Обработать данные                           | -       |
| 201 | Создан документ          | Сохранить Ref_Key                           | -       |
| 400 | Неверный запрос          | Показать ошибку пользователю                | Нет     |
| 401 | Неверная авторизация     | Проверить credentials в настройках или .env | Нет     |
| 404 | Заказ/документ не найден | "Заказ не найден"                           | Нет     |
| 500 | Внутренняя ошибка 1С     | "Временная ошибка. Попробуйте ещё раз"      | Да (3х) |
| 502 | Bad Gateway (nginx)      | "Сервис временно недоступен"                | Да (3х) |
| 503 | Service Unavailable      | "Сервис временно недоступен"                | Да (3х) |

#### 3. XSS и injection защита

- Все данные от пользователя экранируются перед отображением
- GUID проверяются регулярным выражением, а строковые значения в OData-фильтрах экранируются;
  динамические части URL кодируются через `encodeURIComponent`
- PDF генерируется на сервере с контролируемыми данными
